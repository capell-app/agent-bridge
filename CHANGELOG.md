# Changelog

All notable changes to `capell-app/agent-bridge` will be documented in this file.

## Unreleased

- The knowledge server needs a token with the `capell.knowledge.read` scope (or `*`), offered on the token form, and its capability catalogue and schema no longer list class names, policy abilities, required packages or audit events. The knowledge server also serves the README and docs of Capell packages installed under `vendor/capell-app`. Upgrading: give tokens that use the knowledge server the new scope.
- The Laravel Boost preview tool refuses a capability that is not visible on the site server, runs a capability's policy ability for the acting user, and previews a mutating capability only when an ability vouches for the caller. A capability can implement `ResolvesCapabilityPolicySite` so its policy ability is checked in its site's permission team on every entry point, which stops a user whose role is held on that site alone being refused.
- Staff tokens and their audit entries join Privacy Centre exports and erasures: erasing a staff member revokes their tokens, clears the address they were created from, deletes their pending confirmations and clears the browser and address fingerprints on their audit entries.
- A page edit or new draft page from a connected assistant can be undone from its audit entry on the user page. Undo rolls the page back to its version before the change, or deletes the untouched draft. It needs the page's site and permission to roll back or delete pages, and it is refused once the page has changed since or a page has been added under the new draft. Upgrading: run the migration; changes made before it cannot be undone this way.
- Request quotas count a request before deciding, so a burst of concurrent requests can no longer pass the per-token or per-address limit together. The token form offers only the capabilities a token can run. Site state counts are kept to the sites a site-limited token, or an owner assigned to some sites, can reach. A user model without `isGlobalAdmin` or `hasRole` is now refused site access instead of raising an error.
- A token can be limited to chosen sites and capabilities, and given its own requests-per-minute quota, from the Tokens relation on the user page. Site limits narrow every site and page lookup while a capability runs, and capability limits also hide other capabilities from listings and suggestions. The token as stored is checked on every request and confirmation. Upgrading: run the migration; existing tokens stay unlimited.
- High-risk changes from a connected assistant, which include every draft edit and upload, now need the approval of the person the token acts as. They approve or decline the exact preview under Confirmations on their user page in the admin; until then confirming returns `approval_required` and nothing changes. Previews that need approval stay open for an hour (`approval_ttl_minutes`), and `human_approval_risks` chooses which risk levels need it. Upgrading: run the migration; assistants must handle `approvalRequired` in preview responses.
- The knowledge server serves an allowlist. Package documentation is served whole, and application documentation under `README.md` and `docs` only when its front matter sets `agent_knowledge: true`. `agent_knowledge: false` withholds any document, and hidden folders, files over 256 KiB and links outside the application are never served. Upgrading: `public_docs_paths` is replaced by `agent_knowledge.published_paths` and `agent_knowledge.opt_in_paths`; a published config that still sets `public_docs_paths` has those paths treated as opt-in, so mark the documents agents should read.
- Reading a knowledge document returns structured content with its provenance, and package metadata gives repository-relative paths instead of server paths.
- Capability results, Boost previews and audit queries carry a `contentTrust` block naming the fields that hold content written by people, so clients treat them as data rather than instructions.
- Upgrading: tokens that were created without an expiry date now expire 90 days after the upgrade migration runs (the `token_default_lifetime_days` setting). Connected clients keep working until then; rotate or recreate their tokens before that date.
- Every new token expires. The expiry defaults to 90 days and cannot be more than 365 days ahead (`token_maximum_lifetime_days`).
- Token creation IPs are stored as keyed hashes, and existing plaintext values are hashed by a migration.
- Previewed confirmation payloads are stored redacted. Expired confirmations are pruned one day after expiry, and the prune command reports audit entries and confirmations separately.
- Declared the configurable knowledge MCP endpoint and its security middleware in the security inventory.
- Verify token digests in constant time after selecting candidates by a digest prefix; previously issued tokens remain valid.

- Added a machine-readable MCP capability schema resource for agent discovery and compatibility checks.
- Prepared package metadata and documentation for ongoing Capell 0.0.x package work.
